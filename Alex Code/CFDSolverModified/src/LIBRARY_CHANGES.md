# CudaBandedLib changes required by the CFD integration

Per your preference the C++/CUDA is treated as static wherever possible: the
delta arrays, RHS scalings, and boundary-condition flags are all handled in
Fortran (`AlexCudaCompatibility.f90` / `time_step_Q2D.f90`). One backend
change is irreducible: a `shift` parameter so the library solves
**(L + shift*I) x = b** instead of **L x = b**. Alex's `EVD_Thomas` applies
`pdum = -(Ckor/Htime)*Dtm + Lamby(j) + Lambz(k)`, i.e. temperature and the
three velocities are *Helmholtz* solves. This cannot be emulated from Fortran:
any Laplacian the library can build from deltas has structurally zero interior
row sums, so no choice of inputs represents L + shift*I, and fixed-point
iteration around the Poisson solve diverges at your shift magnitudes
(~1e6-1e7 vs smallest |lambda| ~ 10).

The implementation is cheap: your Thomas kernel already passes
`eValsY[row] + eValsZ[layer]` into each tridiagonal solve, and the 2d/3d
kernels divide by `valsX + valsY + valsZ` — all three variants read
`eigen.vals.y` from device memory **at solve time**, so adding `shift` once to
`vals.y` right after construction implements the Helmholtz operator on every
path with zero per-solve cost. A nonzero shift also de-singularizes the
all-Neumann operator, so `isSingular` is cleared (otherwise the kernels would
incorrectly zero the (0,0,0) spectral mode).

## 5. Verify the shift before running the CFD code

Quick unit check (host side, any small grid): build a solver with
all-Dirichlet BCs, some `shift = s != 0`, and a known `x*`; form
`b = L x* + s x*` by calling the solve of an unshifted solver in reverse or by
a hand-rolled matvec, then confirm `solve(b) == x*`. Cheaper still: for a
uniform-grid Dirichlet case the spectrum is analytic, so
`solve` of `b = (lambda_ijk + s) * v_ijk` for a single eigenvector `v_ijk`
must return exactly `v_ijk`.

## 6. Staggered mode for VariableSegment (needed for exact CPU/GPU agreement)

**Correction to earlier guidance:** for the cell-centred axes (temperature and
pressure on all three axes, the two tangential axes of each velocity, the
Potential y-axis), the current VariableSegment operator differs from Alex's at
the wall-adjacent rows **even on a uniform mesh**, not only on stretched ones.
With deltas `d = HPx` (so `d_0 = h/2, d_1 = h` uniformly at a wall),
VariableSegment builds the standard nonuniform 3-point row

    main = -2/(d_0*d_1) = -4/h^2 ,   next = 2/(d_1*(d_0+d_1)) = 4/(3h^2)

while Alex's finite-volume flux row at the first cell is

    main = -(1/(W_0*d_0) + 1/(W_0*d_1)) = -3/h^2 ,   next = 1/(W_0*d_1) = 1/h^2

where `W_0 = Hx12(0) = h` is the true cell width. Interior rows agree wherever
the mesh is locally uniform (`W_i = (d_i + d_{i+1})/2`) and differ on
stretched regions. Both discretizations are consistent and second-order
convergent, so the physics is fine either way, but CPU and GPU solutions will
differ at truncation level near walls until this is implemented. The
node-centred axes (staggered axis of each velocity, Potential x/z) already
match Alex's operator EXACTLY on any mesh, including boundary rows and both BC
types -- verified algebraically against EVD_lapVx / EVD_lap_Fi.

**Implementation.** Add a staggered mode to VariableSegment (this is the
natural meaning for the currently-ignored `isStaggered` flag on the
variable-delta path). Given the n+1 deltas `d_0..d_n` (wall-to-centre,
centre-to-centre, ..., centre-to-wall), precompute the n cell widths ON THE
HOST (the recursion is sequential) and upload them as a second device array:

    W_0 = 2*d_0
    W_i = 2*d_i - W_{i-1}      for i = 1..n-1
    (consistency check: W_{n-1} must equal 2*d_n)

Then build rows from widths and deltas (0-based row r = Alex's i = r+1):

    interior:        prev = 1/(W_r*d_r),  next = 1/(W_r*d_{r+1}),  main = -(prev+next)
    Dirichlet start: same formulas with the "prev" neighbour being the wall;
                     main = -(1/(W_0*d_0) + 1/(W_0*d_1)), off = 1/(W_0*d_1),
                     rhs += wallVal/(W_0*d_0)
    Neumann start:   main = -1/(W_0*d_1), off = 1/(W_0*d_1), rhs += flux/W_0
    (end rows mirror the start rows)

This reproduces Alex's EVD_laptmpr / EVD_lapP / tangential-velocity operators
exactly, so after this change all six solvers should agree with the CPU
solvers to solver tolerance (~1e-11 relative) on any mesh -- which is what the
validation harness in this package checks. This touches BoundaryConfig /
AxisSegment template plumbing that you know best, so it is specified rather
than patched.

## 7. Note on nonzero boundary values

All boundary values in this code are homogeneous (0), so the
`boundaryCorrection` adjToB term is zero and needs no scaling. If you ever use
nonzero boundary values together with the RHS scaling described in
`AlexCudaCompatibility.f90` (temperature rhs x GrPr, velocity rhs / DGr), the
boundary correction would need the same scaling. Moot for now; recorded so it
does not bite later.
